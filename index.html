校園閒置物品流通平台

資料庫管理期末專案

組別：第 19 組

專案動機

  • 問題背景：
    • 校園內常有短期需求的物品（如：活動道具、露營器材）。
    • 購買昂貴且造成浪費，缺乏借用管道。
  • 現有問題：
    • 缺乏有效的物品流通機制
    • 沒有信任基礎的借用平台
    • 資源浪費與重複購買

解決方案

  • 核心特色：
    • 建立具備實名制（需使用校內信箱註冊）的借用平台
    • 透過貢獻度系統鼓勵分享
    • 完整的預約與借出流程管理
  • 預期效益：
    • 提升資源利用率
    • 建立校園共享經濟生態

NoSQL 的應用 (MongoDB)

  • 為何選擇 MongoDB？
    • Schema-less: 彈性記錄各種事件
    • High Write Throughput: 適合大量日誌寫入
  • 資料分流：
    • PostgreSQL: ACID 交易 (預約、庫存)
    • MongoDB: Analytics (使用者行為、系統日誌)

關鍵技術：交易與併行控制

解決「超賣」與「Race Condition」問題

1. Isolation Level & Locking


# reservation_service.py

# 1. 設定 Serializable 隔離層級
db.session.execute(
    text("SET TRANSACTION ISOLATION LEVEL SERIALIZABLE")
)

# 2. 使用 FOR UPDATE 鎖定資源 (檢查時段重疊)
session.execute(text("""
    SELECT rd.rd_id FROM reservation_detail rd
    WHERE rd.i_id = :i_id
    AND ((rd.est_start_at, rd.est_due_at) OVERLAPS (:start, :end))
    FOR UPDATE OF rd
"""))

3. Retry Mechanism


# item_service.py (update_item)
max_retries = 3
for attempt in range(max_retries):
    try:
        # ... 執行交易 ...
        db.session.commit()
        break
    except OperationalError as e:
        if "could not serialize" in str(e):
            time.sleep(0.1 * (attempt + 1)) # Exponential Backoff
            continue
        raise e

遇到的困難

  • PostgreSQL Serialization Failure：
    在高併發下頻繁失敗，透過 Retry 機制解決。
  • 複雜的時段重疊邏輯：
    使用 SQL `OVERLAPS` 運算子簡化判斷。
