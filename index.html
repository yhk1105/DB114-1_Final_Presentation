Our things - 校園閒置物品流通平台

資料庫管理期末專案

組別：第 19 組

專案動機

  • 問題背景：
    • 校園內常有短期需求的物品（如：活動道具、露營器材）。
    • 購買昂貴且造成浪費，缺乏借用管道。
  • 現有問題：
    • 缺乏有效的物品流通機制
    • 沒有信任基礎的借用平台
    • 資源浪費與重複購買

解決方案

  • 核心特色：
    • 建立具備實名制（需使用校內信箱註冊）的借用平台
    • 透過貢獻度系統鼓勵分享
    • 完整的預約與借出流程管理
  • 預期效益：
    • 提升資源利用率
    • 建立校園共享經濟生態

系統架構

技術棧說明

  • 前端： Web Frontend （JavaScript + HTML/CSS）
  • 後端： Python Flask + SQLAlchemy
  • 關聯式資料庫： PostgreSQL （儲存交易資料）
  • NoSQL 資料庫： MongoDB （儲存使用者行為紀錄）

資料庫設計 （ER Diagram）

核心表格：Member, Item, Reservation, Loan, Contribution

核心 Table 關聯 - Member

  • Member （會員）
  • 關聯：
    • Member 1 : N Item （物品）
    • Member 1 : N Reservation （預約單）
    • Member 1 : N Contribution （貢獻紀錄）

核心 Table 關聯 - Item

  • Item （物品）
  • 關聯：
    • Item N : 1 Member （物品擁有者）
    • Item N : 1 Category （物品分類）
    • Item 1 : N Reservation_Detail （預約明細）

核心 Table 關聯 - 預約單相關

  • Reservation & Reservation_Detail & Loan
  • 關聯：
    • Reservation 1:N Reservation_Detail （預約明細）
    • Reservation_Detail 1:1 Item （物品）
    • Reservation_Detail 1:1 Loan （借用單）
  • Reservation_Detail 負責處理時段衝突

NoSQL 應用（MongoDB）

  • 為何選擇 MongoDB？
    • Schema-less：彈性記錄使用者行為
    • High Write Throughput：大量使用者行為資料寫入
  • 資料分流：
    • PostgreSQL：ACID 交易（預約、庫存、借用）
    • MongoDB：Analytics（紀錄使用者行為、漏斗圖分析）

設計思維：
我們針對系統中 Loading 最重的「時段重疊檢查」建立了複合索引，這直接提升了併發預約時的鎖定與查詢效率。

交易與併行控制

交易時防止同時預約同一物品的相同時段，以及貢獻度修改時鎖定貢獻度紀錄

1. Isolation Level & Locking

  • Isolation Level: SERIALIZABLE
    • 確保交易序列化執行，防止時段衝突
  • Pessimistic Locking (FOR UPDATE)
    • 鎖定貢獻度紀錄
    • 防止重複使用貢獻度

# reservation_service.py
db.session.execute(text("
    SET TRANSACTION ISOLATION LEVEL SERIALIZABLE"))

# 鎖定貢獻度紀錄 (防止併發修改)
session.execute(text("""
    SELECT i_id FROM contribution
    WHERE m_id = :m_id 
    AND is_active = true
    -- ... 其他條件 ...
    FOR UPDATE OF contribution
"""))

2. 交易控制與併行控制時序圖

sequenceDiagram participant A as User A participant DB as DB participant B as User B Note over A,B: 1. 搶訂時段 (Serializable) A->>DB: Begin Tx B->>DB: Begin Tx A->>DB: Check Overlap B->>DB: Check Overlap A->>DB: Insert & Commit Note right of A: OK B->>DB: Insert & Commit Note right of B: ❌ Serialization Failure
sequenceDiagram participant A as User A participant DB as DB participant B as User B Note over A,B: 2. 雙重花費 (Locking) A->>DB: Select For Update Note right of A: 🔒 Lock B->>DB: Select For Update Note right of B: 🛑 Wait A->>DB: Update & Commit Note right of B: 🔓 Unblock B->>DB: Read (Active=F)

3. 交易控制實測 (Live Demo)

  • 場景：兩個使用者同時預約同一熱門物品的相同時段。
  • 預期行為 (Serializable Isolation)：
    1. User A 與 User B 同時查詢時段，皆顯示可用。
    2. User A 先完成預約並 Commit。
    3. User B 嘗試提交時，資料庫偵測到 Serialization Failure。
    4. User B 的交易被系統Rollback，預約失敗。
